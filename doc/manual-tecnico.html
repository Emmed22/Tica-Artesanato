Antes de escrever código

O projeto começa pela base que todos vão compartilhar. Não começamos pelo HTML da tela nem por classes isoladas — e não começamos pela infraestrutura antes de entender o que estamos vendendo.

Por que esta ordem? Primeiro entendemos o domínio do negócio (o que é vendido e como o pedido se move entre status) — isso vira contrato de dados. Depois o banco vira contrato de dados técnico; a API vira contrato de integração; as interfaces consomem esse contrato. Essa sequência reduz retrabalho e permite que as frentes avancem conectadas.

🧶01 · produto & catálogo

O que a vitrine vende

Antes de qualquer tabela ou tela, é preciso travar o modelo de produto — a peça de crochê tem cor e tamanho de referência na vitrine, mas o cliente pode pedir diferente.

Decisão fechada: cada produto cadastrado (ex.: "Tapete oval", "Chinelo adulto", "Pano de prato barrado") tem uma cor e um tamanho de referência, usados para exibir a foto e o preço-base na vitrine. Na hora de montar a sacola, o cliente escolhe a cor e o tamanho que realmente quer — que podem ser diferentes dos valores de referência. Essa escolha real fica registrada em item_pedido, não em produto.

Atributos do produto

🏷️

Categoria

Tapete, chinelo, toalha, pano de prato — texto livre definido pela Tica no cadastro.

🎨

Cor de referência

Referência à tabela cor, cadastrada livremente pela Tica (ver abaixo). Usada só para exibição na vitrine.

📏

Tamanho

Enum fixo P / M / G / UNICO — peças de crochê têm poucas variações reais de tamanho.

⏱️

Tempo de produção

tempo_producao_dias — cerca de 2 dias, usado só como informação para o cliente, não trava o fluxo.

Cor — cadastro livre, não lista fixa: cores vivem numa tabela própria (cor) que a Tica cadastra e edita pelo painel, sem depender de deploy ou de mexer no banco — mesmo padrão usado no projeto irmão PM Bem-Casados para tons de cor. Isso evita reabrir o schema toda vez que surgir um fio novo.

Agora o cadastro do cliente entra no MVP — isso não é um ajuste pequeno: implica nova tabela cliente, tabela de tokens de link mágico, envio de e-mail transacional e uma segunda trilha de autenticação, além de expandir os dados pessoais armazenados (o oposto da minimização que justificava a ausência de cadastro). 📍 Endereço completo

Não é cálculo de frete

O sistema pede o endereço completo de entrega (rua, número, complemento — não necessariamente o endereço do cliente, apenas um local válido para entrega) e consulta a API pública ViaCEP para resolver cidade/bairro automaticamente. A Tica decide o valor do frete com essa informação na mão, do jeito que já decide preço hoje. Calcular o valor do frete via transportadora fica fora do escopo (exigiria peso, dimensões e integração com Correios/SuperFrete).

✅ Consentimento

Checkbox antes de enviar

Checkbox não pré-marcado antes de "Solicitar Encomenda", autorizando o envio dos dados à Tica via WhatsApp. Timestamp do consentimento é gravado em pedido.consentimento_lgpd_em.

DBML · item_pedido — a escolha real do cliente
// cor_escolhida_id/tamanho_escolhido podem divergir da referência do produto —
// é aqui, não em produto, que mora o que o cliente realmente pediu.
// produto_id agora é OPCIONAL: pedido personalizado não nasce de um produto do catálogo.
Table item_pedido {
  id uuid [pk]
  pedido_id uuid [ref: > pedido.id, not null]
  produto_id uuid [ref: > produto.id] // nulo quando é item 100% personalizado
  eh_personalizado boolean // true quando produto_id é nulo — evita ambiguidade de "nulo por bug" vs. "nulo por design"
  quantidade int
  cor_escolhida_id uuid [ref: > cor.id]
  tamanho_escolhido tamanho_produto
  personalizacao text // obrigatório quando eh_personalizado=true: é a única descrição da peça
  preco_unitario_registrado decimal // snapshot; em item personalizado, começa nulo e é preenchido pela Tica ao mover para EM_PRODUCAO
}
Por que registrar preço no item? Assim como no projeto irmão, o preço do produto pode mudar depois que o pedido foi feito. preco_unitario_registrado congela o valor combinado naquele momento — sem isso, o histórico de pedidos mudaria de preço retroativamente.
PENDÊNCIA Item personalizado sem produto_id quebra qualquer regra de negócio escrita em cima de "todo item tem produto" (ex.: ProdutoService calculando indicadores por produto na seção 11). O backend precisa tratar produto_id nulo explicitamente em todo lugar que hoje assume presença dele — não é só relaxar o not null no banco.

🔀03 · máquina de status

Fluxograma do status_pedido

Depois que o pedido chega pelo WhatsApp, ele passa a existir como registro no sistema e percorre uma máquina de estados controlada pela Tica.

Caminho principal

💬 RECEBIDOpedido chegou pelo WhatsApp
🧵 EM_PRODUCAOTica está confeccionando
🎁 PRONTOpeça concluída
🚚 ENTREGUEpedido finalizado

Desvio — cancelamento

🚫 CANCELADOpor desistência ou combinação com a cliente
RESOLVIDO NESTA REVISÃO A regra dos 5 dias substitui a pendência de cancelamento sem prazo. Um pedido em RECEBIDO não muda de status sozinho — a mudança continua 100% manual, feita pela Tica no painel. O que existe agora é um lembrete: se o pedido ficar 5 dias corridos em RECEBIDO sem a Tica agir, o sistema dispara um e-mail avisando. A partir do lembrete, ela decide: mover para EM_PRODUCAO (informando a estimativa de prazo) ou CANCELADO.

Lembrete automático — 5 dias em RECEBIDO

⏰ GATILHO

Job agendado

Uma rotina diária (@Scheduled no Spring) verifica pedidos com status = RECEBIDO e criado_em há 5 dias ou mais, sem transição registrada em pedido_status_historico desde então.

📧 AÇÃO

E-mail para a Tica

Envia um e-mail (não para o cliente) listando os pedidos parados, com link direto para o painel. A Tica decide manualmente: mover para produção (com estimativa) ou cancelar.

PENDÊNCIA Ainda falta decidir: o lembrete dispara uma vez no dia 5, ou repete enquanto o pedido continuar parado (diariamente, semanalmente)? Sem essa regra, o job pode implementar qualquer um dos dois comportamentos de forma "correta" e ainda assim frustrar a Tica na prática — validar com ela antes de fechar a implementação.

Estimativa de prazo, ao mover para produção

Quando a Tica muda o status de RECEBIDO para EM_PRODUCAO, o sistema pede uma estimativa de data pronta (pedido.estimativa_pronto_em). Esse valor é só uma referência para ela e para o cliente logado acompanhar — não trava nem valida contra tempo_producao_dias do produto, porque pedidos personalizados não têm produto de referência com esse tempo.

Tabela de transições permitidas

DeParaQuem acionaObservação
RECEBIDOEM_PRODUCAOTicaExige informar estimativa_pronto_em.
RECEBIDOCANCELADOTicaManual — geralmente após o e-mail de lembrete dos 5 dias.
EM_PRODUCAOPRONTOTicaPeça concluída.
EM_PRODUCAOCANCELADOTicaManual — casos excepcionais.
PRONTOENTREGUETicaFim do ciclo de vida do pedido.
Toda transição é registrada em pedido_status_historico, com o horário da mudança — mesmo padrão de auditoria do projeto irmão PM Bem-Casados, mas sem coluna de "responsável" (só existe uma administradora).

🔐08 · integração & segurança

Autenticação, notificações & LGPD

Agora existem duas trilhas de autenticação: a Tica por senha, e o cliente por link mágico. Isso também cria uma nova responsabilidade: enviar e-mail.

ADMIN

JWT + Spring Security

  • BCrypt para senha.
  • POST /api/auth/login retorna JWT.
  • /api/admin/** exige token válido (inclui produto e cor).
  • Angular usa AuthGuard.
CLIENTE

Login por link mágico

  • Sem senha — cliente só tem e-mail e nome.
  • POST /api/auth/cliente/solicitar-link: recebe e-mail, cria/reaproveita cliente, gera magic_link_token e envia por e-mail.
  • GET /api/auth/cliente/validar?token=: valida token (não expirado, não usado), marca usado_em, retorna JWT de cliente.
  • GET /api/pedidos/meus (protegida) lista só os pedidos do cliente_id do token.
ANTI-ABUSO

Limite de cliques

  • evento_clique guarda ip_hash, nunca o IP puro.
  • Limite de cliques por IP em curto intervalo, sem exigir login nem captcha.
  • Protege a qualidade dos indicadores da seção 11.
PONTOS EM ABERTO — LOGIN DO CLIENTE Três decisões que o time precisa fechar antes de codificar, porque mudam o contrato da API:
  • Reenvio de token: se o cliente pedir um novo link antes do primeiro expirar, o token antigo é invalidado ou os dois continuam válidos? (Recomendado: invalidar o anterior — evita múltiplos tokens ativos por cliente.)
  • E-mail não cadastrado ainda: como o cadastro nasce durante a montagem do pedido (seção 02), o primeiro "solicitar link" também cria o cliente. Confirmar que a rota faz upsert, não só busca.
  • Sessão do cliente: quanto tempo o JWT de cliente dura? Diferente do admin (que loga toda vez), um cliente pode querer voltar dias depois só para ver o status — token de vida curta força ele a pedir link de novo com frequência.

Notificações por e-mail

→ CLIENTE

Link mágico de login

Único e-mail que vai para o cliente. Contém só o link de autenticação — nenhum dado do pedido no corpo do e-mail, para não vazar informação caso a caixa de entrada seja compartilhada.

→ TICA

Lembrete de pedido parado

Job diário (seção 03) avisa a Tica sobre pedidos há 5+ dias em RECEBIDO. É o único e-mail que ela recebe do sistema — o resto da gestão continua no painel.

PENDÊNCIA Provedor de e-mail ainda não definido (SMTP próprio, SendGrid, Resend, Mailtrap para dev). Sem isso, Spring Boot Starter Mail não tem para onde configurar host/porta/credenciais — resolver antes de implementar as rotas de link mágico.

📄 Aviso de privacidadetexto curto na vitrine
MINIMIZAÇÃO ENFRAQUECIDA NESTA REVISÃO A versão anterior justificava minimização por guardar só CEP, não endereço completo, e por não ter cadastro de cliente. As duas premissas mudaram: agora há e-mail, nome e endereço completo por pedido, associados a uma conta que persiste entre pedidos. Isso é uma decisão de negócio legítima (o cliente pediu para acompanhar o pedido), mas o aviso de privacidade da vitrine precisa ser reescrito para refletir o que de fato é coletado agora — o texto antigo ficaria desatualizado.
PENDÊNCIA Retenção de dados ainda não tem prazo definido — e agora pesa mais, porque cliente e magic_link_token persistem além de um único pedido. Por quanto tempo manter a conta do cliente e o histórico de pedidos depois de ENTREGUE ou CANCELADO precisa ser combinado com a Tica antes de decidir arbitrariamente.

💻09 · frontend

Construir a web com Angular

A web concentra a vitrine pública e o painel da Tica — com telas de gestão de produto e de cor.

Escolha: separar por features permite que o time trabalhe em paralelo e mantém vitrine, sacola e administração organizadas.
Criar o projeto
ng new tica-artesanato-web --routing --style=scss
cd tica-artesanato-web
ng generate module core
ng generate module shared
ng generate module features/vitrine --routing
ng generate module features/sacola --routing
ng generate module features/admin --routing
ng generate module features/auth --routing
ng generate module features/cliente-auth --routing
ng generate module features/meus-pedidos --routing
01

models/

Interfaces TypeScript alinhadas aos DTOs da API — Produto inclui corReferencia e tamanhoReferencia; ItemPedido inclui corEscolhida, tamanhoEscolhido e ehPersonalizado.

02

core/services

ProdutoService, CorService, PedidoService, AuthService (admin) e ClienteAuthService (link mágico) via HttpClient.

03

features/

Vitrine → sacola → cadastro por link mágico → endereço → WhatsApp. O cliente pode voltar depois, autenticado, para ver o status.

ADMIN

Tela · Gestão de produtos

Formulário de cadastro com categoria, preço-base, cor de referência (dropdown alimentado por cores) e tamanho de referência.

ADMIN

Tela · Gestão de cores

CRUD simples de texto livre — a Tica cadastra e inativa cores sem depender do time técnico.

CLIENTE

Tela · Solicitar link mágico

Campo de e-mail, mensagem "verifique sua caixa de entrada" — sem feedback de "e-mail existe ou não" (evita enumeração de contas cadastradas).

CLIENTE

Tela · Meus pedidos

Lista os pedidos do cliente autenticado com status atual e, quando disponível, estimativa_pronto_em.

🐳12 · deploy

Docker + CI/CD

O banco já está hospedado no Supabase — o Docker aqui empacota só backend e frontend. Este é o ponto em aberto mais importante da entrega atual, e o tema central da disciplina.

Dockerfile · backend
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY . .
RUN mvn -q package -DskipTests

FROM eclipse-temurin:21-jre
COPY --from=build /app/target/*.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
Dockerfile · frontend
FROM node:20 AS build
WORKDIR /app
COPY . .
RUN npm ci && npm run build

FROM nginx:alpine
COPY --from=build /app/dist/tica-artesanato-web /usr/share/nginx/html
.github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }
      - run: cd backend && ./mvnw test
  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: cd frontend && npm ci && npm run build
Por que no final da construção? Docker e CI/CD empacotam e verificam o que já foi construído. Colocar Docker depois que backend e frontend existem evita depurar container antes de depurar a aplicação.
PENDÊNCIA PRIORITÁRIA Ainda falta definir onde hospedar o backend Java em produção (Render, Railway, ou outro). Sem isso, o pipeline de CI/CD não tem para onde fazer deploy contínuo — resolver isso é o próximo passo antes de fechar esta seção.

ENTRA

MVP

  • Vitrine digital com categoria/cor/tamanho
  • Sacola com escolha de cor/tamanho por item, incluindo item 100% personalizado
  • Cadastro do cliente por link mágico (sem senha)
  • Endereço completo de entrega + resolução via ViaCEP
  • Pedido formatado para WhatsApp
  • Painel admin (produto, cor, status)
  • 5 status de pedido + estimativa de prazo ao entrar em produção
  • Lembrete automático por e-mail para a Tica (5 dias parado em RECEBIDO)
  • Cliente autenticado acompanha status do próprio pedido
  • Consentimento e aviso LGPD
  • Indicadores básicos
NÃO ENTRA

Fora do escopo

  • Pagamento online
  • Cálculo automático de frete via transportadora
  • Chat próprio dentro da plataforma
  • Rastreamento de entrega em tempo real
  • Login de cliente com senha (só link mágico)
  • Múltiplos endereços salvos por cliente
  • IA/ML avançado
Regra de ouro: o que ficou fora do MVP continua fora. Reduzir o escopo garante que o que entra funcione dentro do semestre.
IMPACTO NO CRONOGRAMA Cadastro por link mágico, endereço completo, lembrete por e-mail e pedido personalizado não são ajustes pequenos — se somam a: 2 tabelas novas, uma segunda trilha de autenticação, integração de e-mail transacional e um job agendado. Se o prazo do semestre já estava apertado com o escopo anterior, essa expansão precisa ser conversada com a disciplina antes de assumir que ainda cabe dentro do tempo.
